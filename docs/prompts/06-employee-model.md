### Employee model and lifecycle: implementation prompt

Implement the Employee model and its backend functionality for our ACME Salary Management assessment.

#### 1. Employee fields

Create an Employee model with the following fields:

- `id`: UUID primary key, following the existing project conventions.
- `employee_code`: required, unique, human-readable employee identifier generated by the backend.
- `first_name`: required string, maximum 100 characters.
- `last_name`: required string, maximum 100 characters.
- `email`: required string, normalised by trimming whitespace and lowercasing; validate the format and
  enforce uniqueness at both the model and database levels.
- `department`: required string.
- `job_title`: required string.
- `country`: required string.
- `status`: a controlled set of values, initially `active`, `notice_period` and `inactive`.
- `notice_period_started_at`: nullable datetime.
- `notice_period_ends_at`: nullable datetime.
- `created_at` and `updated_at`: standard Rails timestamps.

Do not add an image/avatar field or cloud-storage integration now. Do not add unnecessary fields or
associations.

#### 2. Employee code generation

Generate employee codes automatically on the Rails backend. HR must not supply the code manually.

Use the format `INC-YYYY-NNNNNN`, for example `INC-2026-000101`, `INC-2026-000102`, `INC-2027-000103`, where:

- `INC` is the company prefix;
- `YYYY` is the employee's joining year, derived from the creation/joining date;
- `NNNNNN` is a globally increasing sequence number, not a counter that resets each year.

Implementation requirements:

- Use a PostgreSQL sequence or another concurrency-safe database mechanism.
- Do not generate the next number by counting employee records or using `Employee.maximum(...) + 1`.
- Enforce a unique database index on `employee_code`.
- Generate the code on the server during employee creation.
- Make sure normal creation flows can't accidentally accept a caller-supplied employee code.
- Keep the UUID as the internal primary key, and use `employee_code` as the human-readable identifier.
- Gaps in sequence numbers are acceptable.
- Handle validation failures and database constraint errors using the project's existing error-response
  conventions.
- Inspect the existing UUID and migration conventions before implementing. Avoid changing global database
  defaults unless necessary.

#### 3. Employee model validations

Add meaningful validations for:

- required first name, last name, email, department, job title and country;
- maximum name lengths;
- email format, normalisation and uniqueness;
- employee code presence and uniqueness;
- allowed status values;
- appropriate notice-period dates when the employee is in `notice_period` status.

Also write the required model tests. Once the model is done, we'll move on to the API endpoints, with proper
authentication and authorization. The notice period starts when HR clicks a notice-period button for that
employee; we'll discuss it when we implement the API endpoints.

We don't need `validate :notice_period_ends_after_start`: when an employee joins there is no notice period
yet, so both dates start as `nil`. Remove that validation. Similarly, this one isn't needed either:
`validates :notice_period_started_at, :notice_period_ends_at, presence: true, if: :notice_period?`. The
notice-period attributes can be `nil`.
